# Выброс и автоподбор — 22 ноября 2026

Сборка: `dist-update-itemlist/L2PacketMonitor.exe`.

В инвентаре ПКМ открывает выброс одной штуки, количества одним действием или
указанного количества по одной штуке. Очередь поддерживает несколько заданий,
резервирование доступного остатка, паузу и остановку. Каждая операция требует
наблюдаемого клиентского запроса, соответствующего серверного DropItem и точного
уменьшения остатка. Неподтверждённое действие автоматически не повторяется;
оставшаяся очередь останавливается. Остановка во время уже отправленного
действия дожидается его подтверждения и не отправляет следующую штуку.

На вкладке «Дополнительные опции» автоподбор включается галочкой. Начальное
состояние — выключен, радиус — 200, пауза после подтверждения — 750 мс.
Подбираются наблюдаемые предметы со статусом present. Перед действием радиус
проверяется заново по позиции в клиенте; перепад высоты ограничен 200 единицами.
Успех требует Action к выбранному объекту, серверного GetItem или DeleteObject для него и
увеличения собственного инвентаря на количество этого предмета. Поэтому
поднятие предмета другим персонажем само по себе не увеличивает счётчик.

По прямому ответу пользователя автоподбор включает предметы, выброшенные самой
программой. На время активной очереди выброса он приостанавливается. Новая
очередь выброса дожидается уже отправленного запроса подбора.

## Обработчики клиента

REA-инвентарь экспортов дискового NWindow.dll обнаружил
`UUIScript::execRequestDropItem`. Evidence:
`ev_d83ab309ab5fb523dac82da173f311581a8424d4af753bd740c007b9afa7c9ed`,
родитель `ev_d3f325f2860499d6e4c2d3a04a6e64feef9730b52b2b398bff0e73797d48214e`.
Его дисковая структура предмета отличается от работающего клиента; адреса и
ABI из этого файла не используются для действий.

Обычным чтением памяти выбранного PID найдены реальные UFunction
RequestDropItem, GetPlayerPosition и RequestAction. Проверенные работающие
обработчики принадлежат одной частной allocation. В `monitor-profile.json`
сохранены их RVA и полные байты с учётом четырёхбайтных перемещений адресов.
Перед действием проверяются версия Engine.dll, идентичность процесса и
соединения, единственное совпадение allocation и байты вызываемых функций.

Выброс использует 136-байтный POD ItemInfo: object ID по смещению 4,
количество u64 по смещению 16. Его передача по значению и очистка 148 байт
стека проверены на штатной цепочке RequestDropItem. Отдельный 32-битный
переходник выполняет обычный обработчик в потоке игрового окна через
WH_GETMESSAGE; обычный GetPlayerPosition вызывается в том же действии.
Штатный обработчик подбора получает object ID и текущую позицию персонажа.

Первый пробный выброс по координатам из предыдущего сетевого окна был
отклонён сервером: запрос наблюдался, но инвентарь не изменился. После перехода
на GetPlayerPosition непосредственно перед вызовом сервер подтвердил выброс.
Все последующие операции используют этот способ получения координат.

## Скиллы

Вкладка «Скиллы» строится только по серверному S→C 5F SkillList. Отдельный
FE F9 00 содержит доступные для обучения следующие уровни и не считается
списком уже изученных умений. ПКМ → «Повысить уровень скилла» принимает
целевой уровень. Следующие уровни запрашиваются последовательно; очередной
запрос отправляется только после клиентского C→S 7C с ожидаемыми ID, уровнем,
типом списка 0 и последующего серверного SkillList с новым уровнем. Если
сервер не подтвердил очередной уровень за 30 секунд, операция завершается
ошибкой и показывает последний подтверждённый уровень. Изменение локальных
строк таблицы не используется для имитации обучения.

«Ввести ID и уровень…» принимает вручную ID и целевой уровень без выбора
строки таблицы. Если ID отсутствует в полном актуальном серверном списке,
обучение начинается с уровня 1. Уже изученный ID начинается со следующего
подтверждённого уровня. Правила доступности и стоимость определяет сервер.

В работающем клиенте найдены UFunction RequestSkillList, RequestAcquireSkillInfo
и RequestAcquireSkill. В профиль включены полные байты оригинальных функций
и перемещения абсолютных адресов. Вызов выполняется тем же переходником в
потоке игрового окна. Аргументы передаются через проверенный штатный FFrame
и IntConst; обработчик получает три целых числа: ID, уровень, тип списка.
При смене подключения обучение прекращается. Автоподбор приостанавливается
на время обучения; активная очередь выброса заканчивается до начала обучения.

- `tests/test_inventory_drop.py`, `tests/test_auto_pickup.py`: количества,
  режимы, подтверждения, остановка, пауза, смена сессии, пропуски захвата,
  отказы и отсутствие автоматического повторения неопределённого вызова.
- Встроенная проверка EXE запускает собственный тестовый 32-битный процесс:
  проверяет ABI, ID и количество, свежие координаты, поток и радиус подбора.
  Этот этап не выполняет действий в игровом клиенте.

Сохранённые runtime-байты лежат в `reports/inventory-drop-analysis/`.
Чтение памяти не является атомарным снимком. Полнота живого подтверждения
относится к успешно расшифрованным интервалам; счётчики синхронизации остаются
в отчётах. Произвольный отправитель пакетов и старые диагностические пробы
не используются для новых действий.
