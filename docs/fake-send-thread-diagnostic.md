# Диагностика `Packet Fake Send Thrd`

## Подтверждено наблюдением

21 ноября 2026 года в 18:00:37 UTC один вызов функции отправки в процессе
`AsteriosGame.exe` был выполнен из временного потока Windows ID `125724`.
Входной полный пакет был `03 00 50` (`RequestSkillList`). Функция вернулась,
но в проверенном захвате сети пакет `0x50` отсутствует. В этот момент клиент
отправил один пакет C→S `0xFF` с текстом
`Packet Fake Send Thrd [0x50] 21896 != 125724 | Error [4353001E]`.
Других C→S `0xFF` в этой записи нет. Соединение продолжило работу; все 42
криптографических интервала в записи проверены по конечным состояниям.

В последующей инвентаризации из 104 потоков процесса `21896` оказался самым
ранним: процесс создан в `13:35:46.753653 UTC`, поток — в
`13:35:46.753655 UTC`. Его точка старта `0x11ea40a8` находится в образе
`AsteriosGame.exe` и совпадает с точкой входа EXE, подтверждённой REA/Ghidra.
Временный поток `125724` уже завершился. Поэтому числа в диагностике совпадают
с ID начального потока игры и потока неудачной отправки. Снимок сделан позже
события и сам по себе не раскрывает инструкцию сравнения.

ID `21896` (`88 55 00 00` в little-endian) найден по двум выровненным адресам
в частной области клиента, включая `0x053a4030`. Короткая функция по
`0x0539208a` вызывает импорт через `0x05301348`, затем записывает результат
`EAX` в `0x053a4030`. Слот импорта `0x053b67e0` указывает на экспорт
`GetCurrentThreadId` 32-битного `kernel32.dll` (RVA `0x141f0`). В этом поле
сейчас хранится `21896`. Таким образом, клиент сохраняет ID текущего потока
при вызове этой функции; назначение всех обращений к полю ещё не установлено.

Передача текста записана в исходящем игровом соединении клиента. Это
устанавливает сторону передачи, но само по себе не определяет место, где
строка была создана. Точный модуль, функция и автор текста пока не
установлены. Обычный поиск ASCII и UTF-16LE литералов `Fake Send Thrd`,
`Send Thrd`, `Packet Fake`, а также фрагментов `Fake` и `Thrd`, не нашёл
совпадений в частной области `0x05300000` (6195 страниц), проверенных областях
рядом с игровым модулем, области `0x20000000`, образе `AsteriosGame.exe` и
17 загруженных файлах игры на диске. REA/Ghidra также не обнаружила
определённых строк `Fake`/`Thrd` в EXE. Литерал может
собираться из частей либо раскрываться во время выполнения. Отсутствие
буквального совпадения не устанавливает происхождение сообщения.

Дизассемблирование ранее сохранённого runtime-снимка функции `0x20466790`
в диапазоне `Engine.dll` показывает
переход через клиентский callback по `0x05386d10`, за которым следует
обёртка отправки по `0x05385c98`.
Оба адреса находятся в частной области процесса; первый переходит на
`0x06876233`, второй на `0x053f4dff`. Точки формирования текста и сравнения
пока не прослежены. Линейная дизассемблировка байтов после этих безусловных
переходов не является исполняемым путём и не служит доказательством.

**Наиболее обоснованная непосредственная причина:** вызов сделан из потока
`125724`, тогда как клиент сохранил ID начального потока `21896` и сообщение
сравнивает эти числа. Вместо запрошенного `0x50` клиент отправил `0xFF`.
Источник сохранённого ID доказан кодом; место самого сравнения пока не найдено.
Не установлено, достаточно ли одного совпадения потоков для успешной отправки.

## Возможные объяснения

- **Несовпадение потока выполнения.** Совпадение обеих величин с ID начального
  и временного потоков, а также прямой вызов `GetCurrentThreadId` при записи
  начального ID делают это ведущим объяснением. Неизвестно, сравнивается ли
  текущий ID потока именно с полем `0x053a4030` либо с другим значением.
- **Нарушение последовательности вызовов.** Функция могла требовать вызова
  после постановки операции в клиентскую очередь, а не прямого входа.
- **Состояние соединения.** Неверный этап или объект соединения мог привести
  к той же диагностической ветке. В наблюдаемой записи соединение было живым,
  но состояние конкретной функции до вызова не зафиксировано полностью.
- **Внутренняя проверка клиента.** Клиент мог маркировать внешние вызовы.
  По одному сообщению нельзя определить, является ли это защитой, обычным
  инвариантом потока или общей обработкой ошибок.

`Thrd` почти наверняка сокращает английское *thread* («поток»), а `Send`
относится к отправке. По наблюдению сравнивается с начальным потоком игры;
нельзя утверждать, что речь о выделенном сетевом потоке.

## Как проверить на локальном стенде

На собственном минимальном клиенте и сервере логировать ID потока, стек
вызовов, очередь задач, жизненный цикл соединения и момент фактической записи
в сокет. Затем воспроизвести одинаковый корректный запрос из сетевого потока,
из отдельного потока, до подключения и после отключения. Сопоставить
возвращаемое значение функции с сетевым захватом. Для клиентского компонента,
если есть разрешённая локальная копия с символами или журналом, искать
формирование `0xFF` и сравнение с текущим ID потока. Такие опыты различат
поток, порядок вызовов и состояние соединения без подмены потока или изменения
проверок.

## Остаётся неизвестным

Точный модуль и место формирования сообщения; инструкция сравнения и источник
ожидаемого ID в момент опыта; семантика ошибки `4353001E`; необходимость
каких-либо дополнительных условий помимо потока; поведение такого же вызова
в других состояниях.

## Повторная проверка из начального потока — 21 ноября 2026

У окна `Asterios Prime` владельцем оказался поток `21896`. Диагностический
обработчик сообщений сначала проверен на отдельном тестовом процессе, затем
установлен для этого окна; сам диагностический вызов в игру выполнился в
потоке окна. На отдельном процессе проверено, что тот же механизм передаёт
тело пакета тестовой функции отправки.

При следующем опыте функция `Engine.dll` для пакета `03 00 50` вызвана из
потока `21896` и вернулась без исключения. Валидированный захват не показал
`0x50`. Вместо него появился C→S пакет `0xFF` длиной 28 байт с данными
`04 02` и ASCII-текстом `CMPF0: 6B8C11AD [0x50]`. Подтверждение пакета
получено в расшифрованном захвате с проверкой состояния шифра; за время работы
захвата было зарегистрировано три ошибки синхронизации, поэтому
утверждение об отсутствии `0x50` относится к проверенной области захвата.

Во втором опыте сообщение `Fake Send Thrd` не наблюдалось, но отправка
запрошенного пакета не подтверждена. Два разных опыта не устанавливают полный
набор условий успешной отправки. Повторная загрузка диагностической DLL в
отдельном 32-битном процессе дала её базовый адрес `0x6B8C0000`. Значение
`6B8C11AD` соответствует смещению `0x11AD` в этой DLL: непосредственно перед
ним расположена инструкция `call ecx` по адресу `0x6B8C11AB`, вызывающая
функцию отправки; сразу после неё — `add esp, 0x10`. Следовательно, значение
совпадает с адресом возврата вызова из нашей DLL при отдельно измеренной базе.
Это поддерживает гипотезу об учёте адреса вызывающего кода. Адрес загрузки DLL в самой
игре во время опыта отдельно не записывался, а место формирования `CMPF0`
и точное назначение проверки не установлены.

Поиск ASCII/UTF-16LE `CMPF0` и `6B8C11AD` и
числового значения `0x6B8C11AD` в выбранных областях памяти совпадений не дал.
Включать отправку в основном приложении или автоматически повторять такой
вызов без понимания этой ветки было бы преждевременно.

Данные: `reports/native-send-test-02.json`,
`reports/monitor-20261121-193506-e7fd65/packets.jsonl`,
`reports/fake-send-thread-diagnostic/cmpf0-string-search.json`,
`reports/fake-send-thread-diagnostic/cmpf0-value-search.json`,
`reports/fake-send-thread-diagnostic/cmpf0-caller-correlation.json`.

## Дополнительная сверка — 22 ноября 2026

В сохранённом `packets.jsonl` кадр `CMPF0` стоит в направлении C→S между
обычными игровыми пакетами клиента и сервера. Это подтверждает, что данный
текст присутствовал в исходящем потоке клиента. Эта запись не является
входящим ответом сервера; точка создания строки по одному направлению
передачи не определяется. Направление C→S также не исключает зависимости
состояния клиента от предшествующих ответов сервера.

Повторный поиск точных ASCII/UTF-16LE строк `CMPF0`, `Packet Fake Send Thrd`,
`Fake Send Thrd`, `Send Thrd` и `4353001E` в выбранных исполняемых файлах и
ресурсах на диске совпадений не дал. Это согласуется с прежним поиском в
памяти, но не доказывает отсутствия проверки: текст может собираться частями,
раскрываться при работе или находиться в неохваченных ресурсах.

Попытка получить дизассемблирование `Engine.dll` через Ghidra завершилась
тайм-аутом импорта/анализа на 330 секунд. Новых инструкций из этой попытки нет;
она не подтверждает и не опровергает гипотезы о `CMPF0`. На диске DLL имеет
отличающийся от runtime-снимка отпечаток, поэтому её статические байты нельзя
считать точным представлением кода, работавшего во время опыта.

Итог по причинам остаётся разделённым: для `Packet Fake Send Thrd` напрямую
зафиксировано сравнение ожидаемого ID `21896` и фактического ID `125724`; для
последующего `CMPF0` установлены исходящий кадр и отсутствие подтверждённого
`0x50`, а совпадение `6B8C11AD` с адресом возврата DLL — только корреляция,
поскольку её база в игровом процессе во время вызова не измерялась. Семантика
имени `CMPF0`, проверяемое состояние и точный код, формирующий оба сообщения,
остаются неизвестны.

## Проверяемые результаты и состояние программы — 22 ноября 2026

Добавлен отдельный разбор диагностического конверта `FF 04 02`.
В карточке пакета и API доступны `reported_opcode`, `thread_id_left`,
`thread_id_right`, `thread_ids_differ`, `error_code` либо `diagnostic_value`.
Поля потоков названы по расположению в тексте: сам разбор строки не доказывает
источник каждого числа. Значение `CMPF0` не обозначается адресом возврата.
При неизвестной форме сообщения текст сохраняется, а
`diagnostic_format_verified` остаётся `false`.

Оба сохранённых JSONL содержат 1104 записи; проверка u16-длин и SHA-256
декодированных пакетов не выявила ошибок. Найдены две диагностики: одна
`Packet Fake Send Thrd`, одна `CMPF0`. Это проверка сохранённых декодированных
байтов, а не новая расшифровка PCAP. В записи второго опыта по-прежнему учитываются
три ошибки синхронизации, сообщённые прежним монитором; аудит JSONL не устраняет
этот пробел покрытия.

На диске проверены 182 файла в `asterios` и корневой `Asterios.exe`, всего
196498396 байт. Ни одна из строк `CMPF0`, `CMPF`, `Packet Fake Send Thrd`,
`Fake Send Thrd`, `Packet Fake`, `Send Thrd`, `4353001E` в ASCII/UTF-16LE не
найдена. Ошибок чтения и изменений файлов во время этого прохода не было.
Поиск не распаковывает исполняемый код и ресурсы и не раскрывает строки,
собираемые во время работы. Поиск точных строк в интернете также не дал
применимых результатов; общедоступное описание смысла сообщения не найдено.

Сохранённая страница `05300000.bin` имеет корректный PE-заголовок: x86,
9 секций, `SizeOfImage = 0x1833000`, предпочтительная база `0x20000000`.
Оба ранее исследованных callback лежат внутри заявленного этим заголовком
диапазона относительно записанной базы `0x05300000`. SHA-256 заголовка и
страниц callback совпали с manifest снимка. Заголовок не совпал ни с одним
из 41 успешно разобранного кандидата среди 44 выбранных файлов EXE/DLL/BIN.
Это позволяет описать частный PE-образ, но не назвать его файлом-источником
или местом создания сообщения. Снимок сделан до обоих опытов отправки;
его нельзя выдавать за точное состояние памяти в момент `CMPF0`.

Ещё одно непроверенное допущение находится в самой прежней пробе: сигнатура и
контракт функции клиента заданы вручную. Успешное возвращение без исключения
не подтверждает соглашение вызова, корректность аргументов, этап соединения
или разрешённую последовательность операций. Сведения о совпадении ID потока
тоже не проверяют эти условия. Это возможная причина поведения, а не
установленное объяснение `CMPF0`; пробы повторно не запускались.

сохранено в `reports/fake-send-thread-diagnostic/readiness.json`.

Дополнительно сохранена страница входной функции в диапазоне `Engine.dll`:
хеш её 311-байтного префикса совпал с ранее записанным профилем. Потоки клиента
не останавливались, поэтому состояние всех страниц в один момент времени
не устанавливается. Это новый снимок, а не восстановление состояния во время
двух опытов отправки.

Из 643 страниц прежнего набора 639 лежат в диапазоне частного образа. Из них
631 совпала с новым снимком, восемь изменились. Страницы обоих callback совпали.
Различие хешей страницы само по себе не устанавливает изменение кода:
страница может содержать данные, инструкции или оба вида содержимого.
Старые и новые страницы не объединяются в якобы единое состояние опыта.

В текущем снимке также сохраняются значение ID `21896`, прежняя
последовательность вызова импорта `GetCurrentThreadId` и цель его импортного
слота. Место сравнения с фактическим ID потока в диагностической ветке
по-прежнему не установлено.

Для чтения метаданных подготовлена отдельная производная PE-копия сохранённых
байтов памяти. В ней документированы только изменения заголовков, нужные
для представления виртуальных страниц как файловых секций; байты кода и
игровой процесс не изменялись. Стандартный парсер не получил имя компонента
из ресурсов и сообщил ошибки импортного каталога. Поэтому пустые списки
импортов/версий не считаются доказательством их отсутствия. Прямой поиск
`CMPF0`, `Fake Send Thrd` и выбранных связанных строк в текущем сохранённом
образе тоже не дал совпадений. Найденные ASCII-теги `OriginalFilename`,
`FileDescription`, `CompanyName` без соответствующего разобранного блока
версии не устанавливают имя образа.

Сохранённый префикс функции в `Engine.dll` читает первые два параметра из
стека; эти позиции согласуются с базовой формой декларации прежней пробы.
Это уменьшает основание считать весь базовый способ передачи аргументов
ошибочным, но не подтверждает семантику формата, корректность объекта,
внутреннее состояние и допустимую последовательность вызова. Полного
контракта функции по этому фрагменту не получено.

Ограниченный статический разбор callback следует только прямым безусловным
переходам. Он не выбирает ветви по выдуманным значениям регистров и не выдаётся
за трассу исполнения. Вызываемые функции, косвенные переходы, состояние стека
и момент создания текста этим разбором не установлены. Инструкции после
безусловного перехода в старой линейной распечатке по-прежнему не считаются
доказательством исполнявшегося пути.
