# Точная привязка TCP к состоянию клиента

Живая проверка обучения выявила недостаток прежней синхронизации: время
прихода TCP-пакета отличается от времени его обработки клиентом. После
пропуска выбор начала по timestamp мог сдвигаться на соседний MoveToLocation.
В сохранённом примере сдвиг составлял 31 wire-байт, то есть 29 байтов тела.
У обеих ошибочно выбранных границ совпадали конечные ключи и длины, однако
поля SkillList были испорчены через каждые 16 байтов. Это не новый формат
списка и не причина ослаблять его проверки.

Сравнение доказано на одних и тех же данных, без замены ключей:
anchor-counterexample.json (`reports/new-client-decryption/skill-actions/resync-probe/anchor-counterexample.json`).
Running XOR не аутентифицирует содержимое: обратное шифрование и совпадение
счётчика длины сами по себе не доказывают правильность начальной TCP-позиции.

Для проверенной сборки найдено точное подтверждение в памяти клиента:
полный последний расшифрованный пакет сохраняется в `socket+0x850`.
Состояние незавершённого приёма должно быть пустым; альтернативная ветка
приёма по `socket+0xA114` отдельно отклоняется. Пакет входит в два одинаковых
чтения снимка вместе с ключами и счётчиками. Откат счётчика на длину его тела
и шифрование исходных байтов дают точное уникальное совпадение с захваченным
TCP-потоком. Так определяется конец обработанного клиентом пакета, а не
приблизительное время его получения.
native-last-packet-proof.json (`reports/new-client-decryption/skill-actions/resync-probe/native-last-packet-proof.json`).

Исходящее направление привязывается к реально вызванному обработчику:
существующий мост копирует ключ перед вызовом и счётчики отправленных байтов
до/после в том же оконном потоке. Контролируются точная длина и исходный
форматтер. Полный ожидаемый ciphertext команды сопоставляется с TCP, после
чего сохраняется соответствие sequence и счётчика. Короткие повторяющиеся
пакеты сами по себе не выбирают неоднозначную границу. Сессионный ключ не
возвращается из Python-транспорта и не публикуется в API; журнал привязок
содержит только ciphertext и числовой счётчик текущего соединения.

Уже проверенные TCP-позиции сохраняются между окнами. Временное ожидание
байтов не сдвигает исходный снимок и не сбрасывает их. При действительном
разрыве состояния очищаются и заново запрашиваются списки; для привязки
исходящего направления используется штатный запрос меню. Несовпадение,
конфликт или неоднозначность останавливает публикацию окна. Подмена ключа,
поправка plaintext и постоянный сдвиг на 31 байт не используются.

Старые оффлайн-фикстуры без native-пакета проверяют прежний интерфейс отдельно.
Живой профиль содержит новый адрес буфера и всегда использует точную привязку.
