# Захват открытых пакетов внутри клиента

В `ClientTap` подключён проверенный адаптер для Engine.dll
`557c9f6d4f8bed1d517c38d9746d0b1895a440a32ce234f6e40067e6267efb24`.
Он получает исходящие тела непосредственно перед штатным шифрованием, входящие —
после штатной расшифровки. TCP-сегментация, ключи и счётчики шифра для этого
источника данных не нужны. Это адаптер конкретной совместимой сборки, а не
утверждение о поддержке любой неизвестной защиты.

## Проверенные точки

Доказательства ABI и алгоритма сохранены в
`reports/new-client-decryption/203da5b0.asm` и `203da520.asm`.
Таблица виртуальных методов сокета находится по Engine RVA `0x5219bc`.
Слот 31 вызывает шифрование RVA `0x3da5b0`, слот 32 — расшифровку
RVA `0x3da520`. Оба штатных метода принимают три аргумента стека
`body, key_state, size`, используют очистку `ret 0xc` и вызываются через thiscall.

DLL атомарно заменяет только эти две записи таблицы. Байты штатных функций,
ключи, тела и порядок штатных вызовов не изменяются. Каждый callback вызывает
оригинальный метод ровно один раз и сохраняет его возвращаемое значение.
Остальные сокеты с той же таблицей вызывают оригинальные методы без записи.

Исходящие opcode к этой точке уже переставлены сетевым кодом клиента.
Копия нормализуется по текущим таблицам `socket+0xa0d8` и `socket+0xa0e8`
(primary: 209 элементов по 1 байту; extended: 152 по 2 байта, данные vector+4).
Штатный исходящий буфер не изменяется. К копии добавляется стандартная длина
u16LE, чтобы использовать существующие декодеры. Входящий opcode сохраняется.

## Жизненный цикл

Python перед установкой сверяет PID, время создания, endpoint, SHA файла,
отпечатки загруженного кода, активный игровой сокет, обе таблицы opcode и
штатные указатели. Сессионные ключи при этом не читаются и не передаются.
Установка/снятие выполняются на потоке игрового окна через WH_GETMESSAGE,
по тому же механизму, что штатный мост запросов. Никаких служб или глобальных
политик не добавляется.

Один контроллер владеет именованным mutex на PID. Общее кольцо ограничено
128 записями по максимум 32768 байт. Callback готовит копию в своём стеке и
резервирует позицию ограниченным CAS без блокировки копирования другой
дирекции. Callback не ждёт читателя: заполненное кольцо или исчерпание
ограниченного числа конкурентных попыток увеличивает `dropped`. Неподходящий размер
или opcode увеличивает `invalid`. Копии публикуются после заполнения записи.
Контроллер подтверждает чтение после выдачи полного JSON. Python проверяет
весь пакет записей и счётчики до изменения собственной последовательности.

`close()` отключает запись и атомарно возвращает обе исходные записи таблицы.
Закрытие stdin контроллера также запускает снятие. DLL закрепляется в процессе
до выхода игры: незавершённый callback никогда не указывает на выгруженный код.
После обычного снятия тот же процесс допускает повторное подключение с чистым
кольцом. Неожиданное принудительное убийство контроллера не считается
подтверждённым снятием; закреплённая DLL продолжает обеспечивать безопасный
вызов оригиналов, но для восстановления управления требуется учитывать
оставшийся установленный адаптер.

Для закрепления используется неизменяемая копия DLL в каталоге данных
`cache/client-tap/tap-<SHA256>.dll`. Исходный файл сборки можно заменить или
переупаковать, даже пока игра держит прежнюю версию. При повторном использовании
кэша SHA сверяется; изменённая копия отклоняется.

## Проверка

`packaging/build_tap.cmd` собирает 32-битные `tap_hook_v2.dll` и
`tap_controller.exe`. `check_client_tap()` использует эти же DLL и контроллер
на собственном временном процессе. Проверены:

- точное число вызовов оригиналов, их результат, преобразованные байты и ключ;
- нормализация primary и extended opcode, запись входящего пакета после decrypt;
- исключение чужого сокета, 128 записей и 12 учтённых потерь при переполнении;
- одновременная запись 50 входящих и 50 исходящих пакетов максимального размера:
  все 100 записей точны, потери и некорректные записи отсутствуют;
- возврат обоих указателей, повторное подключение к тому же PID с последовательностью
  1, 2, 3 и снятие при EOF.

Живая проверка на запущенной пользовательской сборке зафиксирована в
`reports/new-client-decryption/client-plaintext-tap-live.json`: два независимых
подключения/снятия к одному игровому процессу, нормализованный запрос
`03 00 50`, строгий серверный SkillList с 74 навыками в каждом подключении.
Первый проход: 12 записей (1 C→S, 11 S→C), второй: 10 (1 C→S, 9 S→C).
Оба прохода завершены с `dropped=0`, `invalid=0`; ключи отсутствуют в отчёте.
Игра получила только запрос списка навыков, без изменения персонажа.

Полная проверка Monitor и переключения источников сохранена в
`reports/unified-sources/live-source.json`: auto выбрал client, загружены
74 навыка и 24 позиции инвентаря; реальные запросы `14`, `50`, корневой `23`
прошли через очередь за два цикла с подтверждением всех 6 отправок захватом.
Обновление навыков увеличило ревизию полного серверного списка с 4 до 5.
Затем проверены stop→network (3 окна) и stop→client (повторное подключение).
Во всех трёх фазах итоговые ошибки и потери равны нулю; все рабочие потоки
остановлены и перехват снят. Предыдущая реализация с блокировкой копирования
однажды учла одну конкурентную потерю; этот результат сохранён отдельно в
`live-source-before-concurrent-ring-fix.json`, причина устранена CAS-резервированием.

Публичный Python-интерфейс: `supports(profile)`,
`ClientTap(process, endpoint, profile).start()`, `read()`, `snapshot()`, `close()`.
Профиль:

```json
"plaintext_tap": {
  "kind": "xor64-vtable",
  "encrypt_rva": 4040112,
  "decrypt_rva": 4039968,
  "encrypt_slot": 31,
  "decrypt_slot": 32
}
```
