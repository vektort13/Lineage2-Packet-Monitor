# Серверный источник открытых пакетов

`ServerBridge` в `src/l2_monitor/server_bridge.py` запускает HTTP-приёмник в том же
процессе программы на случайном порту `127.0.0.1`. Случайный токен обновляется при
перезапуске. `snapshot()` не раскрывает его; `configuration()` и экспортируемый ZIP
содержат токен для настройки авторизованного серверного адаптера. Постоянных ключей
расшифровки или игровых сессионных ключей этот путь не требует.

SDK (`src/server_bridge_sdk`) содержит рабочие Python 3 / Java 8 отправители и
точные инструкции. Это адаптер для исходного кода серверной платформы, который
копирует C → S после расшифровки и S → C перед шифрованием. На данном рабочем месте
не внесены изменения в неизвестный сервер: папка MyTestServer содержит клиент.
Проверки ниже относятся к локальному HTTP-обмену SDK, не к живой интеграции сервера.

## Формат и обязательства

POST `/v1/packets`, `Content-Type: application/json`, заголовок
`X-L2-Bridge-Token`. Только локальные Host/Origin, CORS не предоставляется.

```json
{"schema":1,"session_id":"uuid-per-game-connection","protocol":"classic-h5",
 "packets":[{"sequence":1,"direction":"client","hex":"030050","timestamp":1795340000.0}]}
```

Протоколы: `classic-h5`, `asterios-448`, `raw`. Каждый пакет содержит **полный**
u16 little-endian заголовок длины 3–32768 байт. Весь batch валидируется до вызова
потребителя, максимум 128 пакетов/1 MiB JSON, не больше 8 параллельных запросов;
таймаут соединения 3 секунды. Максимум 256 сессий за запуск; переполнение явно
отклоняется. Память прежних sequence не вытесняется с риском принять replay.

`ServerBridge(on_batch)` сериализует приём, вызов потребителя и фиксацию sequence.
Потребитель получает нормализованные `schema,session_id,protocol,packets`, а также
`gap, expected_sequence, first_sequence,last_sequence`. Он **атомарно** проверяет
режим захвата и активную игровую сессию и применяет весь batch. `None`/`True`
означают успешный commit; `False` возвращает 409 без продвижения sequence; исключение
возвращает 503 без продвижения. Потребитель должен проверить всё до изменения
моделей: при исключении после частичного изменения внешний rollback невозможен.

Дубликат, обратный порядок или пересечение с принятой частью возвращают 409 без
повторного применения. Пропуск вперёд принимается с `gap=true`, включая первый
sequence > 1 и пропуски внутри batch. Изменение протокола в той же сессии запрещено.
Направления не имеют независимых sequence: один общий счётчик на соединение.
HTTP 200 означает, что потребитель подтвердил весь batch, а не только получение
байтов сокетом. Смена серверной сессии должна согласовываться с выбранной сессией
в Monitor, чтобы данные разных персонажей не смешивались.

`received`/`accepted_packets` считают принятые пакеты; `dropped`/
`rejected_batches` считают отклонённые HTTP-batch (у невалидного тела количество
пакетов неизвестно). `gaps` считает принятые batch с пропусками. Счётчики sender
`delivered,dropped,failed_batches` отражают его собственную очередь и HTTP-результат.

## Жизненный цикл и экспорт

`start()` идемпотентен, возвращает актуальную конфигурацию;
`export_package(path)` создаёт ZIP с `bridge.json`, обоими sender и README;
`close()` закрывает listener/worker и очищает токен/sequence. Новый запуск создаёт
новый адрес/токен. В frozen-сборке SDK должен находиться в
`ROOT/src/server_bridge_sdk`; приватные захваты в ZIP не включаются.

Callback вызывается под блокировкой приёмника. Потребитель не должен брать эту
блокировку из другой ветки, уже удерживая блокировку модели: снимок bridge следует
получать до захвата блокировки Monitor.

Серверный источник решает получение открытых байтов независимо от игрового шифра.
Разбор полей всё равно зависит от выбранного протокола, а отправка игровых действий
требует отдельного проверенного транспорта. `raw` сохраняет полные байты с честной
пометкой неизвестной схемы.

## Проверки

`python -m unittest discover -s tests -p test_server_bridge.py -v`:
17 проверок локального HTTP-приёмника, полного отклонения невалидного batch,
авторизации/Host/Origin, sequence/дубликатов/пропусков/лимита сессий, callback
commit/reject, параллельных запросов и экспорта. Python SDK реально доставляет
пакеты; переполнение очереди и HTTP-отказ проверены как явные потери с последующим
gap. Обе реализации реально передают по 20 пакетов максимальной длины 32768 байт,
разбивая их на batch меньше 1 MiB без потерь. Java SDK компилируется в Java 8 classfile и реально отправляет оба направления
в локальный приёмник (JDK 23 с `-source 8 -target 8`). Это не проверка внедрения в
живой серверный код.
